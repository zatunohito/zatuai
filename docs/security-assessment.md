# セキュリティ診断レポート (zatuai)

## 調査範囲・方法

対象は `zatuai.vercel.app` を配信している本リポジトリのソースコード全体（`app/`, `lib/`, `next.config.ts`）。
実行環境のネットワークポリシーにより本番サイトへの直接アクセスができなかったため、実サイトへの外部スキャンではなく、そのサイトを構成するソースコードの精査（静的解析・ロジックレビュー）によって診断した。すでに1件のセキュリティ強化PR（レート制限・入力検証・セキュリティヘッダー追加など）がマージ済みであることを確認済み。その上で残っている問題、および新規に見つかった問題を報告する。

## 重要度: High

### 1. `get_notion_status` が非公開Notionページの全文を匿名ユーザーに無条件公開している
- 該当: `lib/tools/notion.ts`, `app/api/chat/route.ts`
- カレンダー側 (`lib/tools/calendar.ts`) は `(公開)` マーカーがない予定を `予定あり` にマスクする仕組みがあるのに対し、Notion側にはそのような選別が一切ない。`getNotionStatus()` はページタイトルと全ブロックのテキストをそのまま返し、チャットボットはログイン不要・認証不要でこの内容をそのまま回答文に含める。
- 影響: インターネット上の誰でも「Notionのステータス教えて」のように聞くだけで、本来は所有者専用と思われる非公開メモの全文を読める。個人情報・未公開の予定詳細・第三者に関する記述などが載っていれば即座に漏えいする。
- 対策案:
  - Notion側にもカレンダーと同様の「公開マーカー」方式（特定のブロック/プロパティのみ返す）を導入する。
  - もしくは、このページ自体を「外部に見せてよい要約専用ページ」として運用を割り切り、個人情報を書かないルールを徹底する（運用に依存するため非推奨）。
  - どうしても全文を見せたくない場合は、このツール自体を無効化するか、簡単な共有シークレット（例: 招待リンクのトークン）を要求する形にする。

## 重要度: Medium

### 2. レート制限が `X-Forwarded-For` の先頭値をそのまま信頼しており、なりすましで回避できる可能性
- 該当: `lib/rateLimit.ts` の `getClientIp()`
- `x-forwarded-for` ヘッダーの最初の値を無条件にクライアントIPとして採用している。プロキシ構成によっては、この先頭値はクライアントが送信したヘッダーがそのまま（あるいは実IPが末尾に追記される形で）残るケースがあり、その場合クライアントは任意の偽IPを名乗ってIP単位のレート制限（`checkChatRateLimit`, `checkNotifyRateLimit`）を毎回無効化できてしまう。
- 影響: DeepSeek API呼び出し（コストが発生する）や、Discord通知（`notify_owner_of_*`、5件/時/IP）のレート制限をIPローテーション不要ですり抜けられる＝コスト増大（デナイアル・オブ・ウォレット）や所有者へのDiscord通知スパムにつながる。
- 対策案:
  - Vercel環境であれば、クライアントが改ざんできない `x-real-ip` やVercel固有の信頼できるヘッダーを優先的に使う（`x-forwarded-for` は補助情報に留める）。
  - どのヘッダーを何段のプロキシまで信頼するかを明示的にドキュメント化し、実際にVercel上で `x-forwarded-for` の値がクライアント操作不可であることを検証する。

### 3. レート制限がインスタンスローカルなメモリのみで、サーバーレスの水平スケールに対して弱い（既知）
- 該当: `lib/rateLimit.ts` 冒頭のコメントで既に自覚済みの制約
- Vercelの関数は同時に複数インスタンスが立ち上がり得るため、実効的な制限値はインスタンス数倍に薄まる。上記#2のIPなりすましと組み合わさると防御がほぼ機能しなくなる。
- 対策案: Upstash Redis や Vercel KV などの共有ストアに早めに移行する（コメントにも同様の意図が記載済みなので優先度を上げることを推奨）。

### 4. CSPの `script-src`/`style-src` に `unsafe-inline` が指定されており、XSSに対する多層防御が実質無効化されている
- 該当: `next.config.ts`
- CSPは設定されているが `script-src 'self' 'unsafe-inline'` のため、万一どこかにインジェクション経路ができた場合でもCSPはインラインスクリプトの実行を止められない。
- 対策案: Next.jsのnonceベースCSP（`middleware.ts` でリクエストごとにnonceを生成し、`<Script nonce={nonce}>` と CSPヘッダーに反映する構成）に移行し、`unsafe-inline` を除去する。styleは影響が小さいため優先度は下げてよい。

## 重要度: Low

### 5. アシスタントの返信をレンダリングする Markdown の `<a href>` にスキーム検証がない
- 該当: `app/page.tsx` の `markdownComponents.a`
- LLMの出力をそのまま `href` に渡している。プロンプトインジェクションでLLMに `[リンク](javascript:...)` のようなMarkdownを生成させられた場合、ユーザーがクリックすると実行される可能性がある（React自体はブロックしない）。CSPの `unsafe-inline` と合わさると実害が出得る。
- 対策案: `a` コンポーネントで `href` のスキームを `http:`/`https:`/`mailto:` のみに制限し、それ以外は無効化するかプレーンテキストとして表示する。

### 6. `notify_owner_of_schedule_request` / `notify_owner_of_inquiry` はLLMが会話から抽出した自由記述をほぼそのままDiscord DMに転送する
- 該当: `app/api/chat/route.ts`
- 文字数の切り詰め（`MAX_FIELD_LENGTH`）以外の無害化がないため、プロンプトインジェクションで所有者のDiscordに任意の文面（フィッシングリンクなど）を送りつけられる余地がある。1時間5件のレート制限はあるが、#2の穴と組み合わさると制限が効かない。
- 対策案: 通知本文に含めるフィールドはMarkdown/URLをエスケープする、あるいは明らかに不自然なリンクを含む場合は警告を付記するなど、所有者側で「これは自動生成された未検証の入力」と分かる注記を強調する。

### 7. リクエストごとの推論コスト（`effort`）をクライアントが自由に選べる
- 該当: `app/api/chat/route.ts`, `app/page.tsx`
- `effort: "max"` を毎回指定でき、かつ1メッセージ最大4000文字×40メッセージまで送信できるため、レート制限の穴（#2, #3）と合わさるとDeepSeek APIのコストを狙って増大させられる。
- 対策案: 匿名ユーザーには `effort` の上限を `high` までに制限する、もしくはIP単位で1日あたりの合計トークン数/コストに上限を設ける。

## 良い点（すでに実装済みの防御）

- 入力メッセージの件数・文字数・ロールの厳格なバリデーション（システム/ツールロールのなりすまし防止）
- カレンダーの日付範囲をサーバー側でクランプ（過去1日〜未来90日）
- カレンダーイベントの `(公開)` マーカーによるプライバシー保護（マスキング）
- ツール呼び出しループの上限（5回）、通知送信回数の上限（3回/リクエスト）
- 汎用的なエラーメッセージ（スタックトレースやシークレットをクライアントに返さない）
- `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, CSPの基本ヘッダー導入
- シークレット（`DEEPSEEK_API_KEY`, `GOOGLE_CLIENT_SECRET`, `NOTION_TOKEN`, `DISCORD_BOT_TOKEN`）はすべてサーバー側 `process.env` のみで扱われ、クライアントへの露出は確認されなかった
- `dangerouslySetInnerHTML` / `eval` 等の危険なシンクは使用なし

## 優先度つき対応リスト

1. **今すぐ**: Notionステータスの全文公開を止める（#1）
2. **早めに**: `X-Forwarded-For` の信頼方法を見直す（#2）、共有ストアへのレート制限移行（#3）
3. **次のイテレーション**: CSPのnonce化（#4）、Markdownリンクのスキーム検証（#5）
4. **余裕があれば**: 通知本文のサニタイズ（#6）、匿名ユーザーのeffort/コスト上限（#7）
